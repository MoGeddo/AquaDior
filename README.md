# أكوا ديور — حضور ومصاريف العمال

تطبيق ويب/PWA لإدارة حضور العمال، المواقع والمشاريع، السلف والخصومات والتسويات. الواجهة عربية ومهيأة للموبايل، والبيانات الحقيقية تُخزّن في Supabase عند ربطه.

> **حالة التدقيق (2026-10-12):** `npm run build` و`npm run lint` ناجحان، و`npm audit` بلا ثغرات معروفة، وSmoke ‏`71/71`. اختُبرت migration محليًا على PGlite لتدفق 350−100−25=225، وتصحيح الخصم قبل/بعد التسوية، وخصوصية إشعارات تجريبية وصلاحيات الخصومات؛ هذا لا يثبت إعداد Supabase/Auth/Storage أو التكامل على Staging. لم تُطبّق أي migration على Supabase في هذا العمل؛ يلزم اختبار Staging قبل النشر.

الوضع التجريبي **لا يعمل تلقائيًا**؛ فعّله صراحةً لأنه يستخدم بيانات وهمية محلية ولا يتصل بقاعدة البيانات:

Demo يبدأ بلا عمال أو مشاريع أو أرقام أو حركات تجريبية. تظهر لافتة تحذير واضحة؛ لا تستخدم هذه الحسابات أو كلمة المرور في التشغيل الحقيقي. قواعد الإنتاج لا تحتوي بيانات Demo.

## الوظائف الموجودة

- العامل: تسجيل حضور اليوم، اختيار موقع/مشروع، طلب سلفة، كشف حسابه.
- الإدارة: العمال والتسجيلات، المواقع والمشاريع، الحضور، طلبات الصرف، سجل الخصومات مع تصحيح آمن يحفظ القيد الأصلي وسببه، التسويات، سجل التدقيق والإعدادات.
- الخصومات والصرف والتسوية تتعامل مع الرصيد العام للعامل ولا تتكرر حسب عدد مشاريعه. سجل الخصم لا يُحذف أو يُعدّل مباشرة؛ التصحيح يلغي القيد مع سبب موثق ويعيد احتساب الرصيد، وحتى تصحيح خصم سبق أن دخل تسوية يصبح رصيدًا دائنًا للفترة التالية.
- إشعارات داخل التطبيق للعامل والإدارة عند الأحداث المهمة، مع تحديث دوري؛ لا يوجد إرسال Push للهاتف عند إغلاق التطبيق.
- قواعد مالية أساسية داخل RPCs في PostgreSQL: ربط هوية العامل بالمستخدم المسجل، كل طلب سحب ينتظر موافقة المالك مهما كان المبلغ، المبالغ المعلّقة تحجز المتاح دون خصم من الرصيد النهائي حتى الموافقة، منع إعادة طلب السحب عند retry بمعرّف واحد، وتجميد اليومية التاريخية للحضور.
- إغلاق المشروع يولّد تسويات ويمنع الإغلاق مع وجود طلبات صرف معلقة.
- RLS وصلاحيات الدوال هي حدود الأمان؛ الواجهة وحدها ليست حدًا أمنيًا.
- بيانات الحساب الوهمي لا تُستخدم كحسابات حقيقية.

## إعداد Supabase — قبل نشر بيانات حقيقية

1. أنشئ مشروع Supabase تجريبيًا وخذ `Project URL` و`anon/publishable key`.
2. استخدم **إما** `supabase/ALL-IN-ONE.sql` **أو** الملفات القانونية بالترتيب التالي؛ لا حاجة لتشغيل الاثنين:
   1. `supabase/schema.sql`
   2. `supabase/policies.sql`
   3. `supabase/triggers.sql`
   4. `supabase/functions.sql`

لـSupabase جديد وفارغ، استخدم `ALL-IN-ONE.sql` مرة واحدة (أو الملفات الأربعة بالترتيب، وليس الاثنين). النسخة المجمّعة تتضمن إعداد الإشعارات، قيد الخصم غير القابل للحذف المباشر وتصحيحه، والتسوية العامة. لقاعدة موجودة، لا تعِد تشغيل `ALL-IN-ONE.sql`: خذ نسخة احتياطية واختبر على Staging مطابقًا للمخطط أولًا، ثم راجع وطبّق يدويًا `supabase/WORKER-SELECTS-PROJECTS.sql` لتدفق اختيار العامل للمشاريع وتحديث السياسات والإشعارات، و`supabase/REMOVE-ATTENDANCE-GPS.sql` لإيقاف إعداد GPS القديم وفرض `NULL` للإحداثيات الجديدة. ميزة تسجيل أيام حضور المالك تحتاج ترحيل `supabase/OWNER-ATTENDANCE.sql`؛ جدولها مستقل ولا يدخل في أجور العمال أو أرصدتهم، فاختبر زر المالك على Staging أولًا. طبّق `supabase/OPERATIONS-NOTIFICATIONS.sql` كترحيل إضافي عند الحاجة لإعداد الإشعارات، و`supabase/DEVELOPER-DELETE.sql` فقط إذا كانت قاعدة Staging لم تحصل بعد على وظائف الحذف للمطوّر. لتحديث طلبات السحب بحيث تنتظر موافقة المالك دائمًا، راجع وطبّق `supabase/WORKER-WITHDRAWAL-OWNER-APPROVAL.sql` على Staging فقط بعد النسخة الاحتياطية؛ لا يحتوي الترحيل على تحديث للسجلات المالية الموجودة. لم تُطبّق هذه الملفات على قاعدة بعيدة ضمن هذا العمل. أما `STAGING-UNIFIED-ATTENDANCE.sql` فهو ترحيل منفصل لقاعدة Staging فقط، ولا يُستخدم على Production.

3. اضبط في بيئة البناء:

```env
VITE_SUPABASE_URL=https://YOUR-PROJECT-REF.supabase.co
VITE_SUPABASE_ANON_KEY=YOUR_PUBLIC_ANON_OR_PUBLISHABLE_KEY
VITE_DEMO_MODE=0
```

المفتاح العام مخصص للعميل ويظل آمنًا **فقط** مع RLS وسياسات صحيحة. لا تضع `service_role` أو مفاتيح Edge Function أو كلمات مرور في متغيرات `VITE_` أو في Git.

### إعداد المصادقة والتسجيل

العامل لا يُدخل بريدًا إلكترونيًا: يكتب رقم الهاتف والاسم وصورة البطاقة واسم المستخدم وكلمة السر فقط. اسم المستخدم يُحوّل داخليًا إلى مُعرّف خاص بـSupabase Auth؛ هذا التفصيل لا يظهر للعامل ولا يستقبل رسائل. لأن التسجيل العام يستخدم `auth.signUp`، يجب على مسؤول المشروع إيقاف خيار **Confirm email** في إعدادات Supabase Auth. إذا كان التأكيد مفعّلًا، قد يُنشأ الحساب بلا جلسة؛ عندها لن يرفع العامل صورة البطاقة، ويلزم للمسؤول إيقاف التأكيد وتفعيل الحساب غير المؤكد يدويًا مرة واحدة. لا تطلب من العامل إدخال بريد أو فتح رسالة تأكيد. لا يوجد تحقق OTP لملكية رقم الهاتف في هذه النسخة؛ موافقة الإدارة ومراجعة البطاقة إجراء يدوي وليسا إثباتًا تقنيًا لملكية الرقم.

لإنشاء أول مالك، أنشئ مستخدم Auth من لوحة Supabase ببريد مثل `ownername@ommal.app` وكلمة مرور قوية، ثم تحقّق من UUID والبريد يدويًا في SQL Editor بصلاحية مالك قاعدة البيانات. مشغّل Auth ينشئ له ملفًا افتراضيًا معطّلًا كعامل؛ بعد التحقق فقط، اربط UUID والبريد بالدور الإداري:

```sql
-- أولًا: اعثر على المستخدم وتحقق من البريد والـ UUID في لوحة Supabase.
select id, email from auth.users where email = 'ownername@ommal.app';

-- استبدل UUID والاسم واسم المستخدم بعد التحقق، وشغّلها في SQL Editor الموثوق فقط.
update public.profiles p
set full_name = 'اسم المالك',
    username = 'ownername',
    role = 'owner',
    status = 'active',
    is_active = true
where p.id = 'VERIFIED-USER-UUID'::uuid
  and p.role = 'worker'
  and exists (
    select 1 from auth.users u
    where u.id = p.id and u.email = 'ownername@ommal.app'
  );
```

لا تستخدم هذا المثال من التطبيق أو من REST API، ولا ترفع UUID حقيقيًا أو كلمة مرور إلى Git. الملف `supabase/setup-accounts.sql` للقراءة فقط ولا ينشئ حسابات.

### اختبارات قاعدة البيانات

`sql/99-test.sql` فحوص قراءة بنيوية فقط؛ **لا** تختبر السلوك الفعلي لـRLS أو التزامن. خذ نسخة احتياطية واستخدم مشروع staging، ثم اختبر مستخدمًا لكل دور وعمليات مرفوضة ومسموحة قبل الإنتاج. ملفات `sql/FUNCTIONS-1.sql` و`sql/FUNCTIONS-2.sql` و`sql/UPDATE-ARCHIVE.sql` قديمة ومعطّلة عمدًا — لا تشغّلها.

## إشعارات الهاتف الخارجية

راجع [`README-PUSH.md`](README-PUSH.md) لإعداد OneSignal، طابور الإشعارات، مفاتيح الخادم، وجدولة الإرسال. لم يُفعّل الربط على مشروع Supabase البعيد.

## Telegram

- أدخل Chat ID من إعدادات التطبيق فقط؛ Bot Token لا يُحفظ في المتصفح أو جدول الإعدادات.
- انشر `notify-telegram`، وخزّن `TELEGRAM_BOT_TOKEN` و`TELEGRAM_CRON_SECRET` ويفضل `APP_ORIGIN` كأسرار Edge Function عبر Supabase CLI. لا تنسخ `SUPABASE_SERVICE_ROLE_KEY` إلى التطبيق.
- التقرير المجدول يرسل `POST` إلى `https://YOUR-PROJECT-REF.supabase.co/functions/v1/notify-telegram?action=daily` مع `x-cron-secret`.
- النشر وإعداد الأسرار وإرسال Telegram **لم تُختبر بعد** في مشروع فعلي.

## المشاريع وتسجيل الحضور

المالك ينشئ المشاريع ويفتحها أو يؤرشفها، ولا يعيّن مشروعًا لعامل بعينه. كل عامل نشط يرى جميع المشاريع المفتوحة ويختار مشروعًا واحدًا أو أكثر عند الحضور؛ لا يوجد حدّ أقصى لعدد الاختيارات. يُنشأ سجل يومي واحد للعامل وتُربط به كل المشاريع المختارة، لذلك لا تتكرر اليومية. سجلات `worker_projects` القديمة تبقى للتوافق التاريخي فقط، ولا تتحكم في إتاحة المشاريع أو قبول الحضور؛ تُسحب صلاحيات الكتابة إليها وتمنع قاعدة البيانات إنشاء تعيينات جديدة.

## الموقع وخصوصية الحضور

تسجيل الحضور لا يطلب إذن GPS ولا يقرأ موقع الجهاز، سواء كان العامل متصلًا أو يعمل دون إنترنت؛ ولا تُرسل إحداثيات جديدة إلى الخادم أو طابور المزامنة؛ وتُزال إحداثيات الحضور التي خزّنتها نسخة أقدم من الطابور قبل المزامنة. يظل اختيار المشروع/الموقع متاحًا لتوثيق العمل. حقلا الإحداثيات محفوظان للتوافق مع السجلات القديمة، ولا يحذف هذا التغيير بيانات GPS التاريخية. لتطبيق منع تخزين الإحداثيات على قاعدة موجودة، راجع وشغّل `supabase/REMOVE-ATTENDANCE-GPS.sql` يدويًا بعد أخذ نسخة احتياطية؛ لا يُنفذ هذا المستودع أي SQL على Supabase عن بُعد.

## Offline / PWA

يخزن Service Worker ملفات الواجهة الثابتة فقط؛ لا تُخزّن بيانات Supabase في كاش المتصفح. يمكن وضع بعض RPCs (الحضور والصرف وإضافة مشروع للحضور) في طابور IndexedDB عند انقطاع الاتصال، ثم يعيد الخادم التحقق عند المزامنة. هذا ليس ضمانًا لقبول العملية: قد يرفضها الخادم إذا تغيّر اليوم أو المشروع أو الرصيد أو الصلاحيات. تظهر العمليات المرفوضة في الشريط مع سبب الرفض، وتتوقف إعادة محاولتها حتى يراجعها المستخدم؛ حذفها يمسح النسخة المحلية فقط ولا يسجلها في الخادم. يجب اختبار فتح التطبيق دون اتصال وسيناريو فشل المزامنة على الأجهزة المستهدفة قبل الاعتماد عليه.

```bash

```

اختبار Smoke يستخدم عينة معزولة داخل jsdom فقط (عاملان وأربعة مشاريع اختبار)؛ لا تظهر العينة في Demo العادي ولا تُضمّن في build الإنتاج. يغطي الحضور المتصل وغير المتصل دون GPS، اختيار أكثر من ثلاثة مشاريع، احتساب يومية واحدة، إشعارات العامل، كشف الحساب، تصحيح الخصم، والتسوية؛ لكنه لا يحل محل اختبار متصفح حقيقي أو اختبار تكامل مع Supabase.

## نواقص معروفة قبل الإنتاج

- خصم الغياب الآلي وموعد قفل اليوم مخزّنان كإعدادات قديمة لكنهما غير منفذين؛ لا يُخصم الغياب تلقائيًا.
- العملة المضبوطة في الإعدادات تخص تنبيهات وتقارير Telegram فقط؛ واجهة التطبيق تعرض الجنيه المصري.
- لا يوجد تحقق OTP للهاتف أو تجربة استعادة كلمة مرور ذاتية؛ تغيير كلمة مرور العامل إداري عبر المطوّر.
- صور البطاقات محفوظة في bucket خاص، لكن لا توجد سياسة حذف/مدة احتفاظ تلقائية لها أو لسجل التدقيق؛ الإحداثيات التاريخية لا تُحذف بهذا التغيير. يلزم تحديد مدد الاحتفاظ قانونيًا وتشغيليًا.
- طابور Offline يخزّن تفاصيل العمليات في IndexedDB بلا تشفير من التطبيق؛ احمِ الأجهزة، وامسح بياناتها عند فقدانها أو تبديل المستخدم.
- التسوية العامة تسجل الصرف بعد تسليم المال فعليًا؛ التطبيق لا يحوّل الأموال ولا يملك تكامل دفع أو إقرار استلام من العامل.
- إشعارات التطبيق تُحدّث دوريًا أثناء الاستخدام؛ لا توجد Push Notifications للنظام عند إغلاق التطبيق.
- المزامنة دون اتصال، وRLS وtriggers وRPCs وEdge Function تحتاج اختبارًا على Staging حقيقي. اختبارات PGlite محلية فقط وليست بديلًا عنه.
- ترحيلا `OPERATIONS-NOTIFICATIONS.sql` و`WORKER-WITHDRAWAL-OWNER-APPROVAL.sql` لم يُطبّقا على Supabase؛ راجعهما وطبّقهما على Staging أولًا قبل النشر. لم يُشغّل أي SQL عن بُعد ضمن هذا العمل. لا تُشغّل ملفات SQL القديمة الموجودة تحت `sql/`.
- لم يُختبر توافق كل نسخة Supabase أو APK/Android؛ خذ نسخة احتياطية وراجع المخطط قبل تطبيق أي migration على بيانات قائمة.

- `src/` — الواجهة والمنطق ووضع Demo وطابور Offline.

- `supabase/ALL-IN-ONE.sql` — نسخة مجمعة متزامنة مع الملفات القانونية.
- `supabase/functions/notify-telegram/` — Edge Function.
- `sql/99-test.sql` — فحوص بنيوية للقراءة.
